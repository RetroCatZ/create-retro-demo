# Retro Demo Creator

## Defaults

Honor explicit user choices. Default is C64 / Modern Times demo with 6 Parts. Default for Amiga ist Amiga 500 / Late Phase with 6 parts. Fidelity of the demo is loosely coupled to the original capabilites and hardware (such as colors, number of sprites etc.), as defined in [platforms](references/plattforms.md). The demo is built on local HTML/assets, a configurable splash screen, and **English** on-screen text, scrollers, menus, and effect information. Precede the splash screen and demo with a short, recognizable startup sequence for the selected computer: C64 BASIC loading for C64 demos, an appropriate Amiga Workbench for Amiga demos, and a platform-appropriate start for other systems. Show the demo being launched; see [browser implementation](references/browser.md). Ask the user to choose an early or late style and the music. Native output or an original binary in an emulator is a separate development path; do not substitute a browser recreation or claim native compatibility.

## Workflow

1. **Brief and reconcile before implementation.** Gather every relevant decision from the user interaction: demo content, platform/era, fidelity, music/runtime, assets, text, parts/scenes, effects, transitions, controls, delivery, technical constraints, and exclusions. Carry forward earlier answers, mark unresolved points, and never invent a user decision. Inspecting existing files, assets, and track duration is planning, not implementation. Ask remaining questions in manageable groups and offer era-appropriate effect choices. Use [briefing](references/briefing.md).
2. **Plan the ending separately.** Ask what makes the final part a climax, its effects, duration, musical cue, text, logo use, and final frame/fade/loop. Give it an editable scrolltext and a scroller technique visibly different from earlier parts.
3. **Document and review the plan before coding.** Write `requirements.md` in the demo project directory before implementing any demo feature. It holds the complete proposed baseline, including a timed part/scene breakdown, requirements and exclusions, assumptions, open questions, and acceptance criteria; make it available for the user to inspect on request. Show a shorter, readable running order in conversation with each part's duration, main effects, and ending. Invite corrections, update `requirements.md` and the summary after revisions, and **wait for the user's decision to proceed**. Once approved, preserve it as the baseline. Keep parts varied, main effects visible, returning graphics deliberately timed, and the separately agreed finale explicit. See [briefing](references/briefing.md) and [effects and eras](references/epochs.md).
4. **Build and track changes.** Prefer straightforward HTML/CSS/JavaScript unless the project requires otherwise. Separate timeline, audio, rendering, controls, configuration, and editable scrolltexts into understandable modules for multipart work. Document code as specified in [code quality](references/code-quality.md). Provide a closed-by-default **Effect info** view with a technical baseline explanation of active effects; only extra depth and links are optional. Drive it, named part boundaries, jumps, music, visuals, and scrollers from one authoritative timeline. Synchronize start, pause, seek, restart, and loop. Let text complete its run. When a source asset changes, regenerate and check every derivative from the new source. On the first requirement or decision change during or after implementation, create `requirements-changes.md` in the same project directory. Record each change's date, old and new decision, source/reason, affected parts/timing/files, and implementation status. Do not silently overwrite the approved `requirements.md`; show material changes and obtain the user's decision before implementing a changed creative plan.
5. **Validate and deliver.** Compare the implementation with the approved `requirements.md` and any entries in `requirements-changes.md`. Check playback, part jumps while playing and paused, audio/visual sync, the promised launch method, and actual appearance. Inspect scrollers and pixel art at normal and enlarged sizes for blur, jerkiness, flicker, clipping, and obscured effects. Deliver code and a concise README with launch steps, hardware profile/fidelity, asset and music provenance, and tests actually performed. See [validation](references/validation.md).
